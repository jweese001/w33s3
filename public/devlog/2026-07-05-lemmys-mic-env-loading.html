Making Lemmy's Mic Automation Find Bluesky Credentials

July 5, 2026

This week I spent my devlog time on a small fix that mattered more than its diff size suggested. The project was Lemmy's Mic, specifically the automation that takes the latest post and shares it to Bluesky on a delay. I had already built the sharing script and the scheduling around it earlier, but this week I ran into a very real automation problem: the script worked in one environment and then quietly depended on credentials being available somewhere else.

That kind of issue is easy to miss when you are testing locally. If your shell already has the right environment variables, everything looks healthy. The trouble starts when the script runs from a scheduler or another machine where the process environment is thinner and less forgiving. In my case, I wanted the Lemmy's Mic share flow to be portable and predictable, not something that only succeeded when launched from the “right” terminal session.

The actual fix

The core change was in share_latest_to_bluesky.py. Before this update, the credential loader checked live environment variables first and then fell back to a global credentials file under ~/.config. That meant repo-local configuration in .env was being ignored, even though that is exactly where this project already keeps other deployment-specific settings.

I added a lightweight load_env_file() helper and changed the credential lookup order so the script now does three sensible things in sequence: check process environment variables, check the repo's .env, and only then fall back to the external credentials file. That sounds boring, but it is the difference between an automation script that is convenient in development and one that is dependable in production.

I also wired the blog root through the credential-loading path instead of hard-coding assumptions about where the script was launched from. That keeps the script grounded in the repository it belongs to. When a workflow depends on local content, images, frontmatter, and social credentials, I want the repository to behave more like a complete application boundary and less like a loose collection of files.

Why I cared enough to test it

Any time I touch automation that posts publicly, I want regression coverage. So I added a test that explicitly clears the relevant environment variables, writes a temporary .env, and verifies that the loader still returns valid Bluesky credentials. That test is important because the bug only appears when the obvious happy path is missing. If I only test with real env vars present, I never exercise the branch that failed in the first place.

This is one of those cases where the lesson is broader than the specific script. A lot of publishing tooling breaks not because the main logic is wrong, but because configuration resolution is fuzzy. The script knows how to find the latest post, parse frontmatter, honor the one-day delay, attach the hero image, and avoid duplicate shares. None of that helps if it cannot reliably answer the basic question, “where are my credentials?”

What's next

I consider this a follow-up hardening pass rather than a new feature, but I like this kind of work because it makes the whole pipeline more trustworthy. The next thing I want to keep watching is the full post-to-share handoff over time: new article lands, the delay rule triggers correctly, the Bluesky post publishes once, and the ledger prevents repeats. This week was about removing one more “works on my machine” assumption from that chain.

It is not the flashiest progress report, but it is honest engineering work. Small operational fixes like this are what let creative systems keep running after the fun part of writing the script is over.
