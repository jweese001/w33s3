Teaching FlowBoard to Remember the Scene

June 28, 2026

This week I spent time on a part of FlowBoard that matters a lot in practice but is easy to undersell in a demo: visual memory. The short version is that I updated a set of FlowBoard project files so they stop behaving like isolated prompts and start behaving more like reusable scene plans. The work happened in one of my creative pipeline repos, where I was refining title-card workflows for a screenplay project, but the underlying problem is pure product work.

The challenge is familiar if you’ve ever tried to generate a sequence of related images with AI. You can describe a character, a room, a prop, and a mood very clearly, and still watch the system drift. Faces change. Environments flatten out. The “same” scene starts feeling like a set of cousins instead of a coherent visual world. FlowBoard already helps by breaking prompts into parts, but this week I pushed further on making those parts remember actual references.

From prompt fragments to reference-aware workflows

The most important change was adding explicit reference nodes into several FlowBoard JSON workflows. Instead of only wiring together style, camera, action, setting, and text nodes, I started attaching portrait references for characters and image references for locations directly into the graph. That turns the workflow into something closer to a visual dependency map. The character node is no longer just “Mason, age 23, art director.” It can now be anchored to a specific portrait reference. Same for a setting like an office or a Victorian house interior.

That sounds small, but it changes how I think about the product. A node graph shouldn’t just be a prettier prompt editor. It should be a place where continuity lives. When I revisit a workflow later, I want to see not just what I asked the model for, but what evidence I gave it.

Upgrading the generation path

I also updated these workflows to target gemini-3-pro-image-preview instead of the older gemini-pro configuration. Some of the diff is just expanded JSON formatting, but the meaningful part is that the projects now preserve richer structure around model choice and reference connections. In practical terms, I’m preparing FlowBoard projects for a generation path where reference fidelity matters more than clever prose.

One thing I like about this direction is that it makes the technical model easier to explain. If I’m building a montage image and I care about the same character appearing across multiple beats, the workflow should show that requirement explicitly. It shouldn’t be hidden in a paragraph and left up to luck.

Why this feels important

I didn’t ship a flashy new UI this week. I didn’t add some giant new feature banner. But I did move FlowBoard a little closer to the version of the product I actually want: a system for composing repeatable image logic, not just one-off prompts with nice boxes around them.

The next step is making this less manual. Right now, I’m proving the pattern in real project files by wiring references into title-card workflows and seeing where the model still slips. From there, I want FlowBoard to make these relationships first-class: clearer reference handling, better continuity tooling, and workflows that can explain why an output stayed on model or drifted off.

That kind of work is slower than a splashy feature sprint, but it’s the sort of foundation that makes everything else more believable. If FlowBoard is going to be useful for narrative image pipelines, it has to remember who is in the scene, where they are, and what visual world they belong to. This week was a solid step in that direction.
